# GMAS symptoms: cause, confirmation, fix

Log lines are quoted by their stable text; `(1.4+)` marks lines and switches that do not exist on trees older than GMAS 1.4. GMAS paths are relative to `Source/GMCAbilitySystem/`; GMC console variables are described in [gmc-diagnostics.md](../../gmc-prediction/references/gmc-diagnostics.md). "Debugger" is the Gameplay Debugger category `GMCAbilitySystem`; "Verbose" means `Log LogGMCAbilitySystem Verbose` on the machine named.

## Attributes

| Symptom | Likely cause | How to confirm | Fix |
|---|---|---|---|
| An attribute reads 0, or a change does not take | The row kept the default clamp, which on 1.4 is an active `[0, 0]` pin (`FAttributeClamp`, `Public/Attributes/GMCAttributeClamp.h`); on older trees the same row floated free | Debugger, *Attributes* row: the value and `RawValue` are 0 on both sides from the first frame. `GetAttributeByTag(Tag)->DumpDebugString()` (1.4+) prints the clamp | Set `Clamp.Max` or `MaxAttributeTag`, or untick `bClampMax`; same for the floor (`gmas:gmas-attribute`, `gmas:gmas-upgrade` after a 1.3 → 1.4 move) |
| Crash at the first bind (access violation inside `BindReplicationData()`) | The ASC's `GMCMovementComponent` pointer is unset: nothing in GMAS assigns it, and the bind dereferences it without an `ensure` (`Private/Components/GMCAbilityComponent.cpp`) | The stack ends in `UGMC_AbilitySystemComponent::BindReplicationData` called from the pawn's `PostInitializeComponents`; the pointer is null in the debugger | Set `GMCMovementComponent = this` in the movement component before calling `BindReplicationData()` (`gmas:gmas-setup`) |
| The attribute does not exist at runtime | The `UGMCAttributesData` asset was added to `AttributeDataAssets` after `BindReplicationData()` ran, or only on one machine | `BL.GMAS.DumpAttrBindMap` (1.4+) lists every bound row of the local player's pawn: the tag is missing. A different list per machine shows as `LogGMCReplication` corrections from the first move | Fill the list in class defaults, the constructor or `PostInitializeComponents` before `Super`, identically everywhere (`gmas:gmas-setup`) |
| `SetAttributeValueByTag` returns `true` and nothing changes | The function is deprecated and its write is commented out (`Private/Components/GMCAbilityComponent.cpp`): it only marks the unbound set dirty | Read it back with `GetAttributeValueByTag` in the same tick | Starting values come from the row or `SetAttributeInitialValue`; changes go through effects or `ApplyAbilityAttributeModifier` inside the move (`gmas:gmas-attribute`) |
| A bound attribute changes on the server but the owning client never sees it (or snaps) | The write happened outside the move (plain server code, `ServerInstantAttribute` on a bound row), so the client's move produced a different value and GMC corrects it | `gmc.ShowClientCorrections` marks a correction each time the write happens | Bound attributes change inside the prediction tick on both sides; server-only writes belong to unbound rows (`gmas:gmas-rules`) |
| `OnAttributeChanged` reports one odd jump instead of the steps you expect | The delegate fires from the ancillary and simulation ticks once per attribute whose value differs from the last check; several changes in a frame collapse, and a correction arrives as one net delta | `Log LogGMCAbilitySystem Verbose` on the client plus `gmc.LogClientReplay`: the jump follows a `Client replay :::` block | Treat the delegate as presentation; decide gameplay from `GetAttributeValueByTag` inside the move (`gmas:gmas-attribute`) |

## Abilities

| Symptom | Likely cause | How to confirm | Fix |
|---|---|---|---|
| An ability fires twice, or its FX play twice on the owner | One-shot work ran on a replayed or combined move: no live-move guard, or no `CL_DoNotCombineNextMove()` after the event (`Source/GMCCore/Public/Components/GMCReplicationComponent.h`) | `gmc.ShowClientCorrections` or `gmc.LogClientReplay` shows a replay at that moment; `GMAS.LogApplyTrace 1` with `GMAS.ApplyTraceFilter` set to the effect class prints two `[ApplyTrace]` stacks with different `action_t` (1.4+); `[ImpulseTrace] ... replay=1` is the replayed impulse (expected and idempotent) | Guard side effects with `!OwnerAbilityComponent->IsReplayingForGMASLogic() && !GetOwnerMovementComponent()->IsSimulatedMove()` (1.4+; the movement component's `CL_IsReplaying()` before) and seal the move (`gmas:gmas-ability`, `gmas:gmc-prediction`) |
| An activation lands about a second late | A server-originated operation the owning client could not apply: every candidate fails its tag checks there, or a batch payload is missing, so the move never acknowledges it and the server forces it when the 1 s grace expires. Before 1.4 every target without an autonomous client (AI, unpossessed pawns) waited the full second | Client: `RPCOnServerOperationAdded: N` (Verbose) with no later `[AckTrace:Client:...] op=N` (1.4+); server: `Forcing Operation On Server` (Verbose, 1.4+) about 1 s later, `[ProcessOp] op=N ... force=1` with `GMAS.LogApplyTrace`, and `[AckTrace:Server:ProcessAck] op=N` never showing `has_grace=1` | Gates on bound tags both sides see, first granted candidate passing on both (`gmas:gmas-rules`); AI targets: upgrade to 1.4 (`gmas:gmas-upgrade`) |
| An ability ends by itself about 2 s after the press | The server never confirmed the client instance within `ServerConfirmTimeout` (2 s on 1.4+, 1 s before): the operation was dropped, refused on the server, or the two sides disagree on the ability id | Client: `[AbilityCut] Client removing unconfirmed ability after 2.00s` (Error, 1.4+) with the diagnostics dump. Server, with `GMAS.LogApplyTrace 1`: `[ServerOpDrop] op=-N reason=...` (never reached the pipeline) or `[ServerOpAccept]` followed at Verbose by `Ability Activation for Ability.Dash Stopped By ...` (refused there) | Same gates and costs on both sides (`gmas:gmas-ability`); an unallowed payload type (`Client operation type ... is not allowed by server as client input`, Error) means a client called a server-only API |
| An ability activates with no resource left, and the cost drives the attribute to 0 instead of refusing | Activation never checks the cost: `PreBeginAbility` runs cooldown, `PreExecuteCheckEvent` and the blocking checks only, then `CommitAbilityCost` applies the cost effect regardless, and the clamp floor (1.4+) pins the result at 0 | Debugger *Attributes*: the resource sits at 0 after the press; no `Stopped By Failing PreExecution check` line at Verbose | Return `CanAffordAbilityCost()` from `PreExecuteCheckEvent` (`gmas:gmas-ability`) |
| The press is swallowed, nothing logs | Grant or map problem, or a second instance refused by the single-instance gate | Verbose: `No Abilities Granted for InputTag` (Error) and the grant lines described in `gmas:gmas-setup`; `[AbilityGate] Activation of X refused: single-instance gate held N s` (Warning, 1.4+) once the blocker is older than 2 s, else `Stopped (Already Instanced)` at VeryVerbose | Fix the map or grant; an instance held open by a task waiting on a payload that never comes is the usual blocker (`gmas:gmas-ability`) |
| An ability is cancelled by its own cooldown right after a correction | Replays restore bound values, not `ActiveCooldowns` or ability instances. Before 1.4 the re-delivered activation met the cooldown the first run armed; a one-instance-per-press design loses the instance that ended inside the replay window on every tree | Client Verbose: `Ability Activation for X Stopped By Cooldown` right after `Client replay :::` lines (`gmc.LogClientReplay`). On 1.4 the re-delivery logs `Activation operation N already consumed on this side (redelivery/replay) — skipped` instead, and the instance is simply gone | Long-lived instances polling a bound input flag; cooldowns predicted logic reads kept as bound floats (`gmas:gmas-ability`, `gmas:gmas-rules`) |
| Abilities on one input tag never start on the listen host, or only some do | Mixed `bActivateOnMovementTick` on one input tag (the first granted candidate decides the tick for the batch); on trees older than 1.4 the host pawn also lost deferred ancillary-tick activations to a second queue drain | `Trying to Activate Ability: X from Movement|Ancillary, but it doesn't match bFromMovementTick state of other abilities` (Error) | One value per input tag (`gmas:gmas-ability`); upgrade for the host-pawn drop (`gmas:gmas-upgrade`) |
| Ability or operation ids differ between client and server | Before 1.4 each side generated `AbilityID` from its own `ActionTimer` (`× 100`, bumped on collision), so an activation processed in different moves (client on the movement tick, server on the ancillary tick, or two presses in one frame) got two ids and the confirm RPC addressed nothing. On 1.4 ids derive from the operation id (`DeriveAbilityIDFromOperation`, `Public/Components/GMCAbilityComponent.h`); only direct `TryActivateAbility` calls still use the fallback | Client `[AbilityCut] Client removing unconfirmed ability` plus server `[TaskDiag] Heartbeat for unknown AbilityID=... op=unattributed` (both 1.4+); `[TaskHeartbeat] Timeout ... last_taskdata_ability_id` naming an id other than the ability's own | Activate only through `QueueAbility`; upgrade to 1.4 (`gmas:gmas-upgrade`) |
| Pre-1.4: a server-side `QueueAbility` on a remote player's pawn never activates; server operations on AI pawns land a second late; a pre-release tree crashes in standalone | On 1.3 `QueueAbility` always queued into the owner-advanced client queue, so an activation the server queued for a remotely controlled pawn never entered a move, silently; server-auth operations applied on a server pawn only once acknowledged, expired or standalone, so AI targets waited the grace. Pre-release trees before 1.4.0 carried two more faults, fixed separately: the tick excluded only the listen host's pawn from the client-payload read, so a standalone pawn (also locally controlled) read client data it never had and crashed; and a remote player pawn was read before its first move arrived (first-frame out-of-bounds in `GenAncillaryTick`); a second queue drain also dropped deferred ancillary-tick activations on the host pawn | The tree is older than 1.4 (`git -C Plugins/GMCAbilitySystem describe --tags`); on the server no `Generated Ability Activation ID` (VeryVerbose) follows the call for that pawn; the crash sits in `GenPredictionTick` (standalone) or `GenAncillaryTick` (a client's first frame) | Upgrade (`gmas:gmas-upgrade`): on 1.4 a server-side `QueueAbility` is a server operation delivered by RPC and AI targets apply on their next ancillary tick; the release notes list the guards |

## Effects and operations

| Symptom | Likely cause | How to confirm | Fix |
|---|---|---|---|
| An effect is missing on one client | Wrong queue type: `Predicted` applied by server-only code has no client instance; `ServerInstantAttribute` (1.4+) never creates one by design; `ServerAuth` called from a client returns `false`. Or the server forced the operation after the grace and the owner never applied it. Cosmetic multicasts are unreliable and can be lost | Debugger *Active Effects* shows `[INCOHERENCY]` (the server count differs from the local one). Server `Forcing Operation On Server` (Verbose, 1.4+) for the operation; `[BatchOp] Sub-operation N payload missing from cache — NOT applied on this side` (Error, 1.4+) on the side that lacks it | Pick the queue type from the table in `gmas:gmas-effect`; design server operations so the owner can apply them (`gmas:gmas-rules`) |
| `Effect X Not Confirmed By Server (ID: N), Removing...` | A `Predicted` effect the server never applied: client-only code path, a server-side apply that failed its tags, a modifier on an unbound attribute, or (pre-1.4) ids that disagree | Error on the client after `ClientEffectApplicationTimeout` (0.5 s, `Public/Settings/GMASNetworkTimingSettings.h`, 1.4+; 1 s before). Server with `GMAS.LogApplyTrace 1`: is there a `[ProcessOp] op=... apply_effect class=X auth=1` at all? | Apply from predicted logic both sides run, on bound attributes (`gmas:gmas-effect`) |
| A removed ticking or periodic effect ends at different times on client and server | On the 1.4 tree the client grace deferral is disabled in `RemoveActiveAbilityEffect` (`Private/Components/GMCAbilityComponent.cpp`): `ClientGraceTime` and `DefaultClientGraceTime` do not affect removal, so each side ends at once and drifts by about one round trip | Debugger *Active Effects*: the effect's `[id: N]` line is present on one side only while the other still ticks it; `gmc.ShowClientCorrections` fires when the bound attribute catches up | Keep the drift acceptable (short ticks) or remove on a bound condition both sides reach in the same move (`gmas:gmas-effect`) |
| An apply fails with `[ApplyAbilityEffect] Action Timer is 0, cannot generate Effect ID. Is it a listen server smoothed pawn?` and returns effect id `-1` | Effect ids derive from `ActionTimer` (the move timestamp), which is 0 before the pawn's first move and on a pawn that is only smoothed, never moved, on this machine (a listen host's view of a remote pawn, a simulated proxy) | The Error (1.4+ wording) on the applying machine; `GetAbilityCutDiagnostics`-style lines show `ActionTimer=0.000` | Apply from inside the target's own move (predicted logic, or a server operation that lands in it), never from a smoothing or proxy context (`gmas:gmas-effect`, `gmas:gmas-rules`) |
| The game stops with a `Fatal` from `[GetNextAvailableEffectID]` (or the server-auth / client-auth variant) saying `overflow` and `Session too long?` | Effect ids are `ActionTimer × 100` plus a per-range offset (`ServerAuthEffectIDOffset = 0x2AAAAAAA`, `Public/Components/GMCAbilityComponent.h`); once the predicted range reaches the next range the component fails fast rather than let ids collide. That takes about 7.16 million seconds of move time, roughly 83 days of continuous server uptime (1.4+) | The Fatal names `ActionTimer`, the id and the offset | Restart long-running servers before that horizon; report the limit upstream if your deployment needs longer sessions |
| A `ServerAuth` or `AddImpulse` call does nothing | Called on a client (`Client attempted to apply server-auth event`, Warning), or the target pawn's move never runs the operation | The Warning on the calling machine; on the server, `[ImpulseTrace] op=N auth=1 ...` (Verbose, 1.4+) absent | Call on the server, on the target's ASC (`gmas:gmas-rules`) |
| `[BatchOp] Sub-operation N payload missing from cache` every frame on the server | Several server operations in one frame were batched; one payload expired or was consumed by another pass. A benign reprocess of an already-applied sub-operation is silent, so a logged line is a real miss | The Error (1.4+) names the sub-operation and the batch size; pair with the client's `[AckTrace:Client:BatchEnd] ... ids=[...]` | Fewer operations per frame on one target, or one effect that carries the whole change (`gmas:gmas-effect`) |
| `Dropped client operation N: payload expired after 256 moves` | The client queued an activation but did not send a move for a whole history (`MoveHistoryMaxSize`, `Source/GMCCore/Public/Components/GMCReplicationComponent.h`): paused, frozen, or not controlling the pawn | The Warning on the client (1.4+); `gmc.LogClientMoveTrace` shows no moves leaving | Queue from input while the pawn is possessed and moving; investigate why moves stopped (`gmas:gmc-prediction`) |
| `[ServerProcessOperation] Rejected ClientAuth ... not whitelisted` | A client-auth ability or effect class is not listed in `ClientAuthorizedAbilities` / `ClientAuthorizedAbilityEffects` (1.4+) | The Warning on the server with the class name | Whitelist it or use the predicted path (`gmas:gmas-ability`, `gmas:gmas-effect`) |

## Tasks

| Symptom | Likely cause | How to confirm | Fix |
|---|---|---|---|
| A key-release task completes immediately | `UGMCAbilityTask_WaitForInputKeyRelease` needs the ability's `AbilityInputAction` (passed to `QueueAbility`) and an input component; without them it completes at once. With them, a key already up at activation ends it too | `UGMCAbilityTask_WaitForInputKeyRelease::Activate: EndOnStart!` (Error) when the key reads released; silent completion one move later when no action is set | Pass `Instance.GetSourceAction()` to `QueueAbility`; an ability driven by a bound held flag polls the flag instead (`gmas:gmas-ability`, `gmas:gmas-task`) |
| An ability is cut on the server after a few seconds while the client still runs it | The server twin stopped receiving heartbeats: the client has no task with that id (tasks created from a tick on one side only, or during a replay), or the client instance is already gone | Server: `Server Task Heartbeat Timeout` (`LogGMCReplication`, Error) and `[TaskHeartbeat] Timeout ...` (`LogTemp`, Error, 1.4+); client: `[AbilityCut] Server force-ended ability that was still active locally` (Warning, 1.4+). `[TaskDiag] Task X registered DURING replay` (Error, 1.4+) names the creation point | Create tasks from `BeginAbilityEvent` or `Completed` handlers only, identically on both sides (`gmas:gmas-task`) |
| `[TaskDiag]` warnings about `never issued on this side` or `Progress payload lost` | Task-id divergence (different task creation order on the two sides) or a payload addressed to an ability only one side has | The Warning (1.4+) lists the max issued id and the live abilities; `op=…, op_known=…, op_consumed=…` says whether the operation was ever delivered here | Symmetric task creation (`gmas:gmas-task`); for the ability-id half see the id-mismatch row above |
| `[TaskDiag]` or `Forcing Operation` lines flood the log | On 1.4 the benign `[TaskDiag]` branches and `Forcing Operation On Server` are Verbose and appear only after you raised the category. On 1.3 the force path logged at Warning (`Client effect operation missed grace period, forcing on server.`, `... has been force apply by the server`) | Read the level in the line itself: on 1.4 these lines carry `Verbose`, and `Log LogGMCAbilitySystem Log` silences them | Lower the verbosity when done, or upgrade (`gmas:gmas-upgrade`). Warning-level `[TaskDiag]` lines are real and belong to the row above |

## Replication and replay

| Symptom | Likely cause | How to confirm | Fix |
|---|---|---|---|
| A simulated proxy shows a stale or default bound value after spawning | GMC applies no replicated state to a simulated proxy for `PostSpawnSmoothingPause` (1 s by default, `Source/GMCCore/Public/Components/GMCReplicationComponent.h`); a value bound with `SimulationMode::None` never arrives | `gmc.ShowNetRole` confirms the pawn is a simulated proxy; `gmc.ShowSimulationDelay`; the value flips after about a second | Identity and spawn data also travel by initial-only actor replication and seed the bound copy (`gmas:gmas-rules`); choose a `SimulationMode` other than `None` (`gmas:gmc-prediction`) |
| Odd or old values in `OnSyncDataApplied` | The hook fires before and after every replayed move and during rollback swaps, with historical states | Check the `EGMC_NetContext` argument; `gmc.LogClientReplay` shows the replay around it | Detect transitions once per frame in `WorldTickEnd` (`gmas:gmc-prediction`) |
| `[ReplayBurst] <Pawn> observed N replay occurrences within W s` | Sustained corrections on the owning client: predicted logic reads something unbound (a replicated property, world time, an unbound member, an attribute changed outside the move), or a bound attribute uses `AlwaysCombineOverwrite` while feeding movement | `gmc.ShowClientCorrections`; `gmc.ForceFullSyncDataValidation 1` plus `gmc.LogClientReplay 1` so the replay dump names every deviating bound value; `BL.GMAS.DumpAttrBindMap` (1.4+) maps a float binding index to its attribute | Move the value into bound state or derive it from bound state (`gmas:gmc-prediction`, `gmas:gmas-rules`); `CombineIfUnchanged` for discrete attributes (`gmas:gmas-attribute`) |
| `[ReplayActivation] op=N ... activated during replay — first delivery` | The move that first carried the activation was discarded or refused on this side, so the replay is the first run here; the other side may hold a different instance | The Warning (1.4+); check whether the server has the ability in the debugger's *Active Abilities* | Usually follows another fault (a dropped move, a refused gate): fix that first |
| Move timestamps and `ActionTimer` differ between the two logs for the same move | No `AGMC_WorldTimeReplicator` in the world (`Source/GMCCore/Public/Replication/WorldTime.h`), so client and server clocks live in different domains | `gmc.LogNetWorldTime`; the `LogGMCReplication` notice that no such actor exists | Spawn exactly one from the game mode on the server (`gmas:gmc-prediction`) |
| `ClientQueuedOperations has N pending operations on server` or `ServerQueuedBoundOperationsGracePeriods has N pending operations on client` every tick | A client-side queue path ran on the authority or the reverse: a role check around `QueueAbility` / server-operation calls is wrong (the bound queue's `CheckValidState`, `Private/Utility/GMASBoundQueueV2.cpp`) | The Error repeats each ancillary tick on the machine named | Route through the ASC's public entry points and check `HasAuthority()` before server operations (`gmas:gmas-rules`) |
| `[GMAS-LIVE-CHECK] Module loaded — build tag ...` at Warning | The module's version banner, logged once per process | Appears once at startup | Nothing; the 1.4 release notes list it as a known noise line |
